# 实验管线验证结果

> 日期：2026-09-23
> 配置：30 任务 × 2 模式 × 3 网络档 × 3 预算档 = **540 次运行**
> 端点：mock 模拟器（`experiments/mock_llm_server.py`）

---

## ⚠️ 首先必须说清这批数据的地位

**这是管线验证，不是论文结果。**

`mock_llm_server.py` 是一个**小模型模拟器**，不是一个模型。它存在的唯一目的，
是在真实模型（Ollama 边缘节点 / 云 API）接入之前，把任务集、决策引擎、prompt 组装、
指标采集、验证器、报表这**整条链路**先跑通并证明其正确，避免把管线缺陷拖到第 14 周才发现。

因此：

| 指标 | 是否可信 |
|---|---|
| prompt tokens | ✅ 可信（由真实 prompt 文本与端点返回的 usage 决定） |
| 成功率 | ⚠️ 仅在"两组可比"的意义上可信，绝对值无意义（模拟器的工具选择是关键词规则） |
| 路由分布 / 云调用数 | ✅ 可信（完全由仓颉引擎决定） |
| 延迟 | ❌ **不可信**，由 mock 按 token 数 sleep 模拟 |
| token 削减比例 | ✅ 可信（两组的 prompt 都是真实组装的） |

**换真实端点只需两个参数**，管线代码不变：

```bash
python experiment.py --edge-url http://127.0.0.1:11434/v1 \
                     --cloud-url https://<cloud>/v1 --model <name>
```

## 2. 核心结果

### 2.1 Token 削减（这是方法的本体收益）

| 模式 | 预算利用率 | 工具注入策略 | Prompt tokens | 相对基线 |
|---|---|---|---|---|
| eager（基线） | 任意 | `eager-all` | **584.4** | — |
| budget | 0.25 | `eager` | 584.4 | 0%（余量充足，正确选择不压缩） |
| budget | 0.55 | `two-stage-top3` | **398.3** | **−31.8%** |
| budget | 0.85 | `two-stage-top3` | **398.3** | **−31.8%** |

**关键点**：调度器在余量充足时（util=0.25）**主动保持全量上下文**，只在预算紧张时才压缩。
这正是设计意图——压缩不是无条件的好事，应当在需要时才付它的代价。

### 2.2 云调用成本

| 网络 | eager 基线云调用 | budget 云调用 | 变化 |
|---|---|---|---|
| wifi + LAN | 30 / 30 | **6 / 30** | **−80%** |
| 弱网 | 0（全部退回设备） | 0（改走 edge） | — |

基线在 wifi 下对**每个**任务都调用云端；调度器只对 6 个高难度步骤调用云端
（其余落到边缘节点），云调用降低 80%。

### 2.3 三层路由的实际价值（弱网场景）

这是重定位后才存在的维度，也是本方案相对现有工作的核心新增点：

| 网络档 | eager 基线落点 | budget 调度器落点 |
|---|---|---|
| wifi + LAN | cloud ×30 | cloud 6 / **edge 24** |
| 弱网 + LAN | **on-device ×30**（完全退回设备） | **edge ×30** |
| 弱网 + 无 LAN | on-device ×30 | on-device ×30 |

**弱网 + LAN 可用时，调度器把 30 次执行全部保住在边缘节点，而基线只能全部退回设备。**
基线之所以退回去，是因为它把"广域网不可用"等同于"无远程选项可用"——
而局域网通常在广域网劣化时仍然存活。这正是"边缘层"存在的理由，也已被数据体现。

### 2.4 成功率

所有 18 个配置组均为 **1.000**。

**结论要谨慎**：在当前 5 工具池 + top-3 设置下，`gold_retrieved_rate = 1.000`，
即金标工具**总能**被选入 top-3，所以压缩是**零代价**的。
换言之，**本实验没有触及压缩的代价那一侧**。见第 4 节。

## 3. 过程中修掉的三个真实缺陷

这一节比结果更重要：它们说明"管线先跑通"这个决定是对的。

### 3.1 沙箱拒绝子进程在系统临时目录写入

Python `tempfile.TemporaryDirectory()` 创建的目录**无法写入**（`PermissionError`），
但会话工作目录可写。→ 改为在 `experiments/_tmp/` 下落地请求/响应文件。

### 3.2 实验设计缺陷：预算档位单一，两组测得完全一样

初版只在 `tokens_spent = cap/4`（util=0.25）单点采样。
由于调度器在余量充足时正确选择不压缩，`eager` 与 `budget` 的 prompt tokens **完全相同**，
实验实际上什么都没比较。

→ 把**预算压力升格为一等实验变量**，引入 `--utils 0.25,0.55,0.85` 梯度。
这是一次典型的"数据看起来正常但实验无效"的错误，只有对齐两组的数值才会暴露。

### 3.3 模拟器保真度不足，制造了恒定假失败

模拟器的工具选择初版让描述词权重过高：`"search my contact list"` 被路由到 `web.search`；
改进后又因为没有语义能力，`"find online the release notes"` 与任何工具名都没有字面重叠，
被路由到 `calendar.create`。表现为 **3 个任务在全部 18 个配置组中恒定失败**。

诊断手段是**按任务聚合失败次数**——恒定性说明问题在模拟器而不在实验条件。
修复分两步：
1. 名称分量权重远高于描述词，且描述词做停用词过滤
2. 引入一个**显式且极小**的同义词映射（online→web、schedule→calendar…），
   模拟真实模型固有的近义理解能力；该映射在代码中公开，不是隐藏的调参

> **教训**：模拟器本身也需要验证。若不做按任务聚合的诊断，
> "90% 成功率"会被当作方法缺陷，而真实原因是测量工具的问题。

## 4. 本实验**没有**回答的问题（下一步）

| # | 未回答的问题 | 为什么 | 怎么做 |
|---|---|---|---|
| 1 | **压缩的代价是什么？** 两阶段注入在什么条件下会选错工具？ | 5 工具池 + top-3 使金标必然入选，代价一侧未被触及 | 扩大工具池到 12–20 个，或把 k 降到 1；使 top-k 真正具有选择性 |
| 2 | 消息表示（natural/summary/structured）对成功率的影响 | 当前单步任务没有多轮 agent 间消息 | 实现 3 智能体循环（Planner→Executor→Verifier） |
| 3 | 真实模型下的数字 | 端点是模拟器 | 接入 Ollama 边缘节点；这一步只换 endpoint |
| 4 | 真实端侧延迟与内存 | 模拟器按 token 数 sleep | 鸿蒙真机 + 局域网边缘节点实测 |
| 5 | 鸿蒙 A2A 协议开销 | 尚未接触真机 | 真机调试链路打通后测量 |

**优先级建议**：先做 #1（改造成本最低、直接触及论文核心论点），再做 #3。

```

├── mock_llm_server.py        OpenAI 兼容模拟推理服务（stdlib，无依赖）
```

`gold_in_selected` / `prompt_tokens` / `cloud_calls` / `success` / `detail`，
足以支撑论文的 Pareto 图与消融分析。

## 6. 复现

```powershell
# 1) 构建并发布仓颉决策引擎
powershell -ExecutionPolicy Bypass -File tools\cj.ps1 -Project agentbudget4cj bin

# 2) 启动模拟推理服务（后台）
python experiments\mock_llm_server.py --port 8100 --decode-ms-per-token 1.5 --prefill-ms-per-token 0.05

# 3) 跑实验
cd experiments
python experiment.py --out results
```
