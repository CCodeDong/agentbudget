## 二、技术路线的三点查证结论（回应"技术路线无法核实"）

这是老师提的第一条批评。**我们查了 SDK 元数据，结论如下**：

| 能力 | 查证结果 | 方案 |
|---|---|---|
| **全文检索** | OpenHarmony 标准 API **无**检索能力；HMS 有 `DataAugmentation.Retrieval` | **自研 BM25（纯 ArkTS）**——零依赖、模拟器可验证 |
| **OCR** | OpenHarmony 标准 API **无 OCR**；`AI.MindSporeLite` 在 phone/tablet/2in1 **均不可用**；只能走 HMS `@hms.ai.ocr.textRecognition` | **HMS OCR + 明确的降级方案** |
| **本机验证环境** | 模拟器**无 HMS Core**；MateBook（2in1）**有** HMS Core，且 OCR 在 2in1 元数据中存在 | **在 MateBook 上实测 OCR** |

### 关键设计：核心功能不依赖 HMS

> **检索（核心）用自研 BM25 → 任何环境都能验证、都能跑。**
> **OCR（增强）用 HMS → 若目标机不可用，应用仍完整可用，只是索引范围缩小到文本类文档。**

**这不是妥协，而是把风险隔离在设计里。** 老师担心的"技术路线无法核实"，
在这一设计下变成："核心路线可在模拟器上逐步验证；增强路线有明确的验证方法与降级路径"。

## 五、"数据不出设备"的具体设计支撑（回应"不能仅停留在口号"）

老师说这条需要"具体设计支撑"。下面是可以逐条证明的：

### 5.1 权限设计：只申请必要的一个

| 权限 | 类型 | 用途 | 为什么必要 |
|---|---|---|---|
| `ohos.permission.GET_NETWORK_INFO` | **读取** | 读当前网络档位，用于调度决策展示 | 不含任何数据外传能力 |

**不使用**：网络访问、通讯录、位置、相机、麦克风、设备标识。

### 5.2 无网络请求：可实测证明

**现状已实测**：代码中无 `http.createHttp` / `request` / `WebSocket` / `fetch`。
**计划**：W8 交付一份"网络请求静态扫描结果"，作为上架材料的支撑附件。

### 5.3 数据流向

```
用户选择的文件
      ↓（文件选择器，用户逐次授权）
应用沙箱目录（/data/storage/el2/base/...）
      ↓
本地索引（自研 BM25，存于沙箱）
      ↓
仅在本机内存中检索 → 屏幕显示
      ↓
   ❌ 无任何出站网络请求
   ❌ 无云端副本
```

### 5.4 可验证的三条

1. **权限清单**可在系统设置中查看（只有 1 个读取类权限）
2. **无网络请求**可通过静态扫描 + 运行时抓包双重确认
3. **数据可删除**：提供"清空索引"入口，删除后文件重新变为未索引状态
