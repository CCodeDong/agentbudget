### 第一部分：为什么做（3 页）

**P3 ｜痛点：手机上的资料"存得进去，找不出来"**
- 资料分散在备忘录 / 聊天记录 / 截图 / PDF
- 系统搜索大多只匹配标题和文件名，**进不去正文**
- 结果：只记得"好像在哪写过这个词"，却找不到
- **【已验证】**：我们的示例资料 109 字，切成 1 个片段即可正文级命中

**P4 ｜现有方案为什么不够（调研结论）**
- 云端笔记类：能搜，但**要联网、要账号、数据在别人服务器**
- 本地文件搜索：能离线，但**不索引正文**（或只索引文件名）
- 系统相册 / 备忘录：各自为政，**不能跨来源检索**

> 原稿 P5 有完整调研表，保留；但要补一列"**能不能离线**"，
> 因为这是我们的差异化所在，不写就体现不出来。

**P5 ｜技术背景与合规边界**
- 鸿蒙端侧能力盘点（文字识别 / 端侧检索 / 智能体框架）
- **【已验证】同一套代码在不同设备上能力不同**：
  | 能力 | MateBook Pro（2in1 / API 23） | 模拟器（phone / API 26） |
  |---|---|---|
  | 文字识别 | 可用 | **不可用** |
  | 智能体框架 | **不可用** | 可用 |
- 结论：**不能假定能力存在，必须探测 + 降级**

> 这是原稿完全没有的一页，也是本项目最有说服力的一页——
> 它是实测出来的，不是推演的。

### 第二部分：我们的三个设计判断（3 页）

**P6 ｜判断一：检索深度不能固定，要看得分分布**
- 固定 k 的问题：内容区分度高时返回太多噪音，区分度低时又不够
- 我们的做法：**看得分分布有没有明显断层**，断层前全留，平坦则取上界
- **【已验证】150 条真实语料查询**：

  | 策略 | 召回率 | MRR | 精确率 | 平均返回 |
  |---|---|---|---|---|
  | 固定 k=3 | 100% | 0.970 | 62.0% | 3.0 |
  | **自适应** | **100%** | **0.970** | **84.7%** | **1.9** |

  **同样的召回与排序质量，精确率高 22 个百分点，少返回 37% 条目。**

**P7 ｜判断二：同一段话不该返回多次**
- 分块有重叠，关键词一出现就同时命中相邻几块 → 用户看到的是"同一段话"重复
- 我们的做法：**合并同文档中重叠或首尾相接的命中**
- **【已验证】**同文档重复查询 **35 → 11（-69%）**，召回率与 MRR 不变
- 一个刻意的取舍：**得分取最高分不累加**（累加会把分块副作用当相关度）

**P8 ｜判断三：识别质量要看"认得够不够多"，不是"认得多准"**
- **【已验证】12 种退化条件的实测结论**：
  | 条件 | 召回 | 精确 |
  |---|---|---|
  | 清晰 / 模糊 / 低对比 / 旋转 / 小字 / 楷体 | 100% | 100% |
  | 行楷（近手写） | 98% | 98% |
  | 强模糊 | 93% | 93% |
  | **小字 + 模糊** | **28%** | **100%** |
- **关键观察：精确率从未低于 100%，除非召回同步下降**
  → OCR 的失败方式是**漏认**，不是**错认**
  → 所以有效性信号是"覆盖率"，不是"语义合理性"

> 这一页是原稿**最缺**的东西：老师说的"无法核实"，
> 在这里变成了"我们自己量化过了"。

### 第三部分：怎么保证数据不出设备（2 页）⭐ 回应批评④

**P9 ｜零权限不是口号，是可核实的**
- **不申请任何系统权限**，包括网络权限
- **【已验证】**安装后「设置 → 应用 → 权限」列表为空
- 那"选图识别""导入文件"怎么做到不需要权限？
  - 用**系统选择器**，不是权限：系统界面取图/取文件，应用只拿到**你选中的那一个**
  - 系统提示语："应用仅可访问您选定的图片和视频，无法访问图库其他内容"
- **为什么要这样取舍**：调相机会要 CAMERA 权限，那就破坏了零权限主张
  → **宁可少一个入口，也不放弃零权限**

**P10 ｜数据全生命周期**
- 存放位置：应用私有沙箱（`/data/app/el2/.../com.xjtu.offlinelib/`）
- 持久化：**只存原始文档，索引启动时重建**（索引格式变化不会让旧档失效）
- **【已验证】**强制杀进程后重启，资料仍在（示例 + 用户新增都验证过）
- 卸载：**数据一并删除，不可恢复**——这是"不出设备"的必然结果，必须在隐私政策里明说
- 整个应用的代码中**不包含任何网络请求**

### P7 具体怎么改（回应"关键路径风险"）

原稿只说"真实模型接入是唯一未知"。修订版要补三件事：

1. **风险的具体形态**：模型端点不可用 / 延迟不可控 / 输出不稳定
2. **降级方案**：`--endpoint` 参数支持模拟与真实切换（老师已建议过）
   - 模拟端点用于保证实验可复现
   - 真实端点用于检验效度
3. **判定标准**：什么情况下算"接入成功"
   - 最小标准：能发出请求并收到符合格式的响应
   - 效度标准：真实端点下的调度决策与模拟端点下的差异在可解释范围内

### P9 具体怎么改（回应"误差传导"）

老师的原话是"补三个信号的估计与误差传导进实验设计"。修订版要把这三条讲清楚：

| 信号 | 怎么估计 | 误差来源 | 误差如何传导到调度决策 |
|---|---|---|---|
| 检索置信度 | 候选得分分布 | 语料规模小 → 分布不稳 | 低估 → 少注入工具 → 漏工具；高估 → 注入过多 → 挤占预算 |
| 信息预算 | 消息长度折算 | 折算系数是经验值 | 高估可压空间 → 压缩过度 → 丢关键信息 |
| 网络状态 | 系统网络探测 | 状态抖动 | 误判在线 → 选错执行位置 → 延迟或失败 |

**并且要说明**：这三条里哪一条目前**有实测数据**、哪一条仍是**分析推演**。

## 五、一句话总结这次改版

**原稿回答的是"我们打算做什么"，修订版回答的是"我们做了什么、用什么证明、还差什么"。**

老师那四条批评里，①②④现在都有实物证据；③（里程碑可验收）靠"验收标准"一列解决。
剩下真正的未知只有一个：**软著什么时候下证**——那是行政周期，不是技术能力。
