> 面向：西安交通大学 · 移动应用开发课程 + 仓颉语言课程 · 最终课程项目
> 日期基准：**2026-09-23**（已用本机系统时钟核验）
> 状态：待用户确认

## 1. 目标定义

本方案要同时服务**三个产出**，且尽量复用同一套代码与实验：

| 产出 | 定位 | 归属 |
|---|---|---|
| **P1 鸿蒙应用** | 可运行的多智能体移动应用（ArkTS） | 移动应用开发课程 |
| **P2 仓颉核心库** | 独立的端侧智能体上下文预算调度库 | 仓颉语言课程 + ICT 编程赛「自主开发三方库」加分项 |
| **P3 一作论文** | 端侧多智能体上下文开销的测量与削减 | 科研目标（雏形，能投就投） |

**约束条件**：单人主力、每周 ≥20 小时、无 GPU 集群、有 HarmonyOS NEXT 真机 1 台、导师资源较弱、可投入周期 ≥1 个月。

## 3. 统一研究主线

### 3.1 一句话叙事

> **多智能体把 token 用量推高到聊天模式的约 15 倍（Anthropic 工程实测），而移动端根本没有 15 倍的预算。**
> 我们把「上下文预算」提升为端侧智能体运行时的一等公民。

### 3.2 研究问题（拟）

在真实移动设备的资源约束下，能否用一个统一的预算模型，**联合**决策以下三件事，从而显著改善「成本–延迟–成功率」的 Pareto 前沿：

1. **本轮向模型注入哪些工具 schema**（全量 eager → 摘要池 + 两阶段懒加载）
2. **智能体之间的消息用什么表示**（自然语言 / 摘要 / 结构化紧凑协议）
3. **这一步走端侧还是云端**（把网络状态纳入路由特征）

现有工作**各自只做一件**：Hera 只做步级路由、Tool Attention 只做工具注入、Anthropic 只报告了 15× 现象。**"三者联合 + 移动端真实约束 + 网络状态"是明确的空白。**

### 3.3 贡献声明（拟）

- **C1（测量）**：首个在真实鸿蒙手机上对端侧多智能体「工具 schema 税 / 通信 token 占比」的端到端定量测量。
- **C2（方法）**：一个预算约束下的联合调度方法（schema 注入 × 消息编码 × 端云路由）。
- **C3（系统）**：用仓颉实现的调度器库 `agentbudget4cj`，验证国产语言在智能体运行时的可行性与性能。
- **C4（发现）**：小模型对结构化消息协议的**能力阈值**与弱网**降级成功率**——两个前人未报告的维度。

### 3.4 故事锋利度自检

- 为什么现在做？→ 端侧多智能体 2026 年才被系统研究，鸿蒙 A2A 2026 年才开放端侧对端。
- 为什么用仓颉？→ 轻量线程（700ns/8KB，十万级）+ 全并发 GC（无 STW）+ 编译期宏，适合做低开销运行时；且官方明确承认 Actor/分布式是空白。
- 为什么必须在手机？→ 云端没有 4k 窗口和内存天花板，比例关系完全不同，云端的测量结论**不可迁移**。

## 4. 系统架构

```
┌──────────────────────────────────────────────────────┐
│  P1 · HarmonyOS 应用（ArkTS）                          │
│  多智能体助手：Planner / Executor / Verifier           │
│  设备能力工具：日历·联系人·文件·通知·网络搜索            │
│  接入 Intents Kit / AI-Agent Framework Kit            │
└───────────────────┬──────────────────────────────────┘
                    │ 优先：进程内/FFI 调用
                    │ 降级：仓颉库编译为本地服务，App 走 loopback
┌───────────────────▼──────────────────────────────────┐
│  P2 · 仓颉核心库 agentbudget4cj                        │
│   ├─ budget/     预算模型（token·时延·费用·电量）        │
│   ├─ schema/     工具 schema 摘要池 + 两阶段加载         │
│   ├─ codec/      智能体间消息编解码（NL/摘要/紧凑）       │
│   ├─ router/     网络感知的步级端云路由                  │
│   └─ telemetry/  埋点与实验数据采集（配套库）             │
└───────────────────┬──────────────────────────────────┘
                    │
┌───────────────────▼──────────────────────────────────┐
│  P3 · 实验与测量层（PC + 真机）                         │
│  端侧模型（INT4 小模型）+ 云 API + 任务集 + 统计分析      │
└──────────────────────────────────────────────────────┘
```

**分层理由**：把「研究核心」全部压进仓颉库，使 P2 成为一个**可独立测试、可独立基准、可开源**的三方库——这同时满足仓颉课程的"实现一个模块"、ICT 的"自主三方库加分"、以及论文的"系统实现"三项要求。鸿蒙 App 负责真实设备约束与演示。

## 5. 仓颉核心库设计（P2）

**命名**：`agentbudget4cj`（遵循 TPC 生态 `<功能>4cj` 约定，如 `protobuf4cj`/`compress4cj`/`httpclient4cj`）

### 5.1 语言特性覆盖（课程评分与论文卖点的交集）

| 仓颉特性 | 在库中的用途 | 为什么非它不可 |
|---|---|---|
| **宏（编译期元编程）** | `@Budgeted` 由工具声明生成紧凑摘要；`@Measured` 自动埋点 | 零运行时开销的 schema 抽取 |
| **模式匹配 + enum** | 消息编解码状态机、路由决策树 | 流式解析的教科书场景 |
| **泛型 + 泛型约束** | `Policy<T>`、向量距离的 `T: Hashable` | 策略可插拔 |
| **扩展 extend** | 给集合加检索/裁剪算子 | API 自然度 |
| **并发 spawn/Future + collection.concurrent** | 并发工具调用、并发测量 | 轻量线程是仓颉第一梯队卖点 |
| **std.unittest（mock + prop_test）** | 预算不变量属性测试 | "任意输入下 token 不超上限" |
| **cjpm bench（@Bench）** | 出 Median/Mean/Err% CSV | 论文实验表直接来源 |

### 5.2 工程交付标准（对标"能被评委当成三方库"）

1. 独立仓库 + 语义化版本 + 提交 `cjpm.toml` 与 `cjpm.lock`
2. README（中英）+ 架构图 + API 文档 + 快速上手
3. `cjpm test --coverage` + `cjcov --html-details` 出 HTML 覆盖率报告
4. `@Bench` + `cjpm bench --report-format=csv`，且与 baseline 对比（`--baseline-path`）
5. Fuzz 测试（`fuzz.fuzz`）——参赛队极少做，差异化强
6. `cjpm build -l`（cjlint 无【要求】级违规）
7. 写清 `bin-dependencies` 引入方式（仓颉无中央仓库，"别人怎么用起来"本身就是加分点）
8. 至少 3 组性能对比：vs 生态同类库、vs 朴素实现、vs 不同参数下的扩展曲线

## 6. 实验设计（P3）

### 6.1 研究问题拆解

| RQ | 问题 | 类型 |
|---|---|---|
| **RQ1** | 工具 schema 税在真实手机上占上下文预算的多少？ | 测量 |
| **RQ2** | 摘要池 + 两阶段懒加载能削减多少 token，成功率损失多少？ | 测量+方法 |
| **RQ3** | 结构化消息协议相对自然语言的收益边界在哪？小模型的解析失败率如何？ | 测量+发现 |
| **RQ4** | 网络感知路由能否改善成本–延迟 Pareto？弱网降级成功率如何？ | 方法 |

**执行顺序：RQ1 → RQ2 → RQ3 → RQ4**（前两个做完即构成一篇完整论文，后两个是增量）

### 6.2 Baselines

- **S1 Eager full schema**（= MCP 默认行为，主 baseline）
- 单智能体无工具（性能下界）
- 全云端智能体（成本/质量上界）
- FrugalGPT 式 cascade
- 任务级路由

### 6.3 指标

token/轮、累计 token、TTFT(ms)、端到端延迟 P50/P95、峰值内存 RSS、成功率、云端调用次数、流量(MB)、**弱网降级成功率**

### 6.4 实验规模

- 硬件：1 台鸿蒙真机 + 1 台 PC
- 端侧模型：1.5B–3B INT4；云端仅少量 API 调用做对照
- 任务：自建 30–50 个设备任务，**规则化 verifier**（避免 LLM-as-judge 不确定性）
- 总运行量：约 300–400 次 agent 运行，单次 10–60s，数小时可跑完
- **零 GPU 训练、零训练成本**
