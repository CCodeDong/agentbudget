## 三、W1（本周）：五项全部启动，一项都不能等

### ① 软著申请 —— 最高优先级

**要准备的材料**（据服务商口径）：

| 材料 | 我们的情况 |
|---|---|
| 身份证明 | 身份证；学生可用**学籍证明**辅助 |
| 源代码 | **前 30 页 + 后 30 页，每页 50 行**（连续编排，注释占比不宜过高） |
| 用户手册 / 设计文档 | 需体现功能逻辑，**不能是简单截图堆砌** |
| 登记申请表 | 中国版权保护中心线上系统 |
| 官费 | 250 元 |

**⚠️ 一个现实问题**：软著要登记的是**「离线资料库」**，而它现在**还没写完**。

**解法（两个选项）**：

| 选项 | 说明 | 风险 |
|---|---|---|
| **A. 先登记调度器**（已有 1,678 行代码） | 材料现成，可立即提交 | 名字与最终应用不一致 |
| **B. 先搭资料库骨架再登记** | 名字对得上 | 拖 2–3 周，压缩开发时间 |

> **我倾向 A**：软著登记的是**软件本身**，不必与上架应用名一致；
> 而且我们**确有一个真实的软件**（调度器库 + 应用，1,678 + 1,478 行）。
> **但这件事必须问老师或版权中心确认**——如果老师要求软著名与应用同名，就得走 B。

**W1 必须完成的动作**：
1. 确认"软著名称是否必须与应用名一致"
2. 备齐源代码（前 30 页 / 后 30 页）与设计文档
3. 在中国版权保护中心提交

### ② 发布签名（AGC）

1. AppGallery Connect → **新建应用**（包名确定后不可改）
2. 证书管理 → 生成 CSR → 上传 → 下载 `.cer`
3. Profile 管理 → 绑定包名 → 下载 `.p7b`
4. 本地生成发布 `.p12` 并**离线备份**

> **`.p12` 丢了 = 应用永远无法更新。**

### ③ 隐私政策与用户协议（可公开访问的 HTTPS 页面）

**最省事的做法：用我们已有的 GitHub 仓库开 GitHub Pages。**

内容至少包含：
- 收集什么数据（**答案是几乎不收集**）
- 如何使用、如何删除
- 联系方式
- **备案号公示位置**（若需要备案）

### ④ 设备方案 —— 这是技术验证的前提

**老师点名的"OCR 技术路线无法核实"，根因就是没有设备。**

| 方案 | 成本 | 可行性 |
|---|---|---|
| 借一台鸿蒙手机（同学/实验室） | 0 | **最高**，优先 |
| AGC 云调试（云真机） | 免费 360 分钟/天 | 需上传 release 签名包 |
| 买一台二手 | 数百至数千 | 保底 |

> **W1 必须定下来用哪条。** 没有设备，W2 的技术验证就做不了，
> 而没有技术验证，整个 OCR 路线就是老师说的"无法核实"。

### ⑤ 确认两个合规问题

在[华为开发者社区](https://developer.huawei.com/consumer/cn/forum/)提问：

> 1. 个人开发者上架 HarmonyOS 应用（非游戏类，纯本地功能，**不发起任何网络请求**），是否强制要求**软件著作权证书**？
> 2. 同上应用，**无服务端、不联网**，是否仍需 **App 备案**？

**这两个答案决定 W1 之后的所有安排。**

## 四、W2：技术验证周（直接回应"无法核实"）

**这一周的唯一目标：把老师说的"无法核实"变成"已核实"。**

| 验证项 | 判据（可验收） | 失败怎么办 |
|---|---|---|
| **OCR 能否跑通** | 真机拍一张讲义，输出可读文字 | 换 SDK 版本 / 试不同 OCR 接口 / 降级到云端（但需备案） |
| **端侧检索能否跑通** | 给定关键词，能命中原文片段 | **改为自建 BM25**（纯 ArkTS，不依赖 HMS） |
| **索引能否在合理时间建完** | 100 页文档索引 < 30 秒 | 调分块策略 |
| **目标设备 API 版本** | 记录实际 API | 若低于 SDK，调整 `compatibleSdkVersion` |

> **必须记住的教训**：`DataAugmentation.*` 属于 HMS kit，
> **很可能和 A2A 一样在缺少 HSP 时直接崩溃**（我们实测过，崩溃日志在案）。
> **所以 W2 的第一件事不是"调用它"，而是"确认它存在且不崩"。**

**W2 产出**：`技术验证报告`（含每项的实测结果、设备型号、API 版本、失败项的降级方案）

## 六、"数据不出设备"的具体设计（回应第四条批评）

**老师说得对：口号不算数。所以做成四层可复现验证。**

| 层 | 做法 | 产出（可给别人看） |
|---|---|---|
| **1. 权限层** | `module.json5` **不声明 `ohos.permission.INTERNET`**，也不声明任何网络相关权限 | 权限清单截图（**只有存储/相机，无网络**） |
| **2. 代码层** | 写一个**脚本**全量检索 ArkTS 源码的网络 API（`http.createHttp` / `request(` / `fetch(` / `WebSocket` / `rcp.`） | **脚本输出：0 匹配** |
| **3. 运行层** | **飞行模式下跑通全流程** | 一段**飞行模式下的完整操作录像** |
| **4. 网络层** | 抓包确认无出站连接 | 抓包截图（或在无网环境证明可用） |

> 第 2 层我们已经给调度器应用写过并跑通过（**零网络请求**），
> 可以直接复用成脚本给资料库用。**这是低成本、高说服力的一层。**

**而且这一套可以写进报告和 PPT**——**"可验证的隐私主张"比"我们很注重隐私"强得多**。

## 十、顺带：老师对仓颉 PPT 的两条建议

虽然你说先聚焦移动应用，但这两条**成本很低、价值很高**，值得一并做：

| 老师的建议 | 怎么落地 | 成本 |
|---|---|---|

| **把"三个信号的估计与误差传导"补进实验设计** | 在论文实验设计里加一节：三个信号的估计误差如何影响调度决策 | **1–2 天** |

> 第二条尤其值得做——它把一个**方法论上的软肋**变成了**严谨性的体现**。
> 这比多加一组实验更能说服审稿人。
