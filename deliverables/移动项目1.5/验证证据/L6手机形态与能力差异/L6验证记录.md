## 三、⭐ 最重要的发现：两台设备的能力几乎相反

| 能力 | MateBook Pro（真机 / 2in1 / API 23） | **模拟器（phone / API 26）** |
|---|---|---|
| OCR 文字识别 | ✅ 可用 | ❌ **不可用** |
| 端侧检索 | ✅ 可用 | ✅ 可用 |
| 视觉基础能力 | ✅ 可用 | ❌ **不可用** |
| **AgentKit** | ❌ **不可用** | ✅ 可用 |

**四项里有两项完全相反。**

### 这个发现说明了什么

**1. 它不是理论上的担忧，而是实测事实**

同一套代码，在真机上有 OCR 没 AgentKit，在模拟器上有 AgentKit 没 OCR。
任何"假定某个能力一定存在"的写法，在其中一个设备上必然出错。

**2. 它直接支撑了本项目的核心设计**

我们当初把 OCR 做成**接口**而不是直接 import，理由是
"避免在缺能力的设备上起不来"。这次实测证明这个理由是真的。

**3. 它也解释了早期那次崩溃**

`@hms.ai.A2A` 在 MateBook 上静态导入导致**加载期崩溃**，
而 CoreVisionKit 在模拟器上静态导入**不崩**（只是 canIUse 为 false）。
说明 HMS Kit 的失败方式并不统一：
- 有的缺 HSP 就在加载期 abort
- 有的能加载，但能力不可用，调用时才失败

**所以不能靠"试着导入一下"来判断能力，必须用 canIUse。**

## 四、优雅降级验证（在无 OCR 的设备上）

在模拟器上点击「运行 OCR 实测」：

| 观察点 | 结果 |
|---|---|
| 界面提示 | **「该设备不支持 OCR」** —— 明确告知，不是静默失败 |
| 应用进程 | **存活，未崩溃** |
| 崩溃日志 | 无新增 |
| 其余功能 | 搜索、资料管理、自测全部正常 |

**这就是设计目标：功能不可用时说清楚，而不是把应用拖死。**
