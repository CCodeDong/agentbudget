# L7 OCR 质量测试（低质量图与近手写）

**日期**：2026-10-24
**设备**：MateBook Pro（HAD-W32）/ 2in1 / API 23
**方法**：同一段 45 字基准文字，12 种退化条件，用**已知答案**算字符级召回/精确率

---

## 一、为什么这样做而不是"看着还行"

"模糊一点还能认出来"不是结论，是感觉。

这些测试图是**我们自己生成的**，所以正确答案已知（生成时写死的基准文字）。
把原文与识别结果都去掉空白后，用**最长公共子序列**比对：

- 召回率 = LCS / 原文字数（原文认出来多少）
- 精确率 = LCS / 识别字数（认出来的有多少是对的）
- F1 = 2PR / (P+R)

> 用 LCS 而不是编辑距离：OCR 输出的换行位置经常和原文不同，
> 那不是识别错误。LCS 只问"这些字有没有被认出来"。

## 三、⭐ 最重要的一条：OCR 的失败方式是"漏认"，不是"错认"

看第 12 行：**召回 28%，但精确率 100%**。

意思是：它只认出了 45 个字里的约 13 个，**但认出来的每一个都是对的**，
没有编造、没有串行、没有把"千"认成"干"。

这个规律在其他行也一致：
- 强模糊：93% / 93% —— 掉了 3 个字，但没有新增错误
- 行楷：98% / 98% —— 掉了 1 个字，无新增错误

**全表 12 行里，精确率从未低于 100%，除非召回率也同步下降。**

### 为什么这条重要

它决定了"识别置信度"该怎么估：

| 如果失败方式是 | 那么合适的信号 |
|---|---|
| 错认（编造内容） | 需要**语义合理性**判断 |
| **漏认（只认得少）** | **字符覆盖率**就够了 |

实测是后者。所以**"识别出的字数相对图片规模太少"就是一个有效的失败信号**。

---

## 四、⚠️ 这同时暴露了当前实现的一个弱点

我们目前的 confidence 是个粗糙代理：

```
blockCount >= 3 ? 0.9 : 0.7
```

**它没有用"字符覆盖率"**，而恰恰覆盖率才是这次实测发现的真实信号。

后果：一张糊到只认出 13 个字的图，如果这 13 个字分布在 3 个块里，
代理会给出 0.9 —— **判成"高质量"，实际是严重漏认**。

**这是当前实现与实测发现之间的偏差，必须记下来。**
正确的做法应该是：用「识别字数 / 图片面积」这类覆盖率指标作为主要信号。

---

## 五、局限（不能含糊过去）

| 局限 | 说明 |
|---|---|
| **合成图 ≠ 真实拍摄** | 没有反光、透视畸变、纸张纹理、手指遮挡、折痕 |
| 退化强度是人工设定的 | 真实照片的退化往往是多种叠加，且不均匀 |
| 单一字体族 | 只用了黑体/楷体/行楷，没有宋体、仿宋、艺术字 |
| 单一基准文字 | 45 字，含中文/英文/数字/等号，但不含生僻字 |
| 结论只对这台设备成立 | MateBook Pro / CoreVisionKit；换设备需重测 |

**所以能说的是**：「Vision Kit 对这几类合成退化相当稳健，
真实拍摄的退化形态（反光、畸变）尚未测试。」

**不能说**：「真实照片识别率 100%。」
