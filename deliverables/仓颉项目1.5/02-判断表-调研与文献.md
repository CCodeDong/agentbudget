# PPT 用的两张表格材料

> 对应大纲：移动应用 P4（现有方案为什么不够）、仓颉 P4（已有工作与空位）
> **说明**：「信号是几个」这一列是**我的归类判断**，不是原文的自述。
> 依据是各工作解决的问题落在几个维度上，不是它们显式声明的信号个数。

## 一、移动应用 P4：现有方案为什么不够

按"能不能离线"和"能不能搜正文"两个维度切分。这两列就是我们的空位所在。

| 类别 | 代表 | 能搜正文 | **能完全离线** | 数据在哪 | 主要限制 |
|---|---|---|---|---|---|
| 云端笔记 | Notion / 语雀 / 印象笔记 | ✅ | **❌** | 厂商服务器 | 要账号、要联网；离线时不可用 |
| 系统备忘录 | 鸿蒙备忘录 / 苹果备忘录 | 🟡 只搜标题与开头 | ✅ | 本机 | **不索引正文** |
| 系统相册文字 | 相册内文字识别 | 🟡 只搜本应用内 | ✅ | 本机 | 只覆盖图片，**不能跨来源** |
| 本地文件搜索 | 系统文件管理 | ❌ 只搜文件名 | ✅ | 本机 | 不进正文 |
| 全文检索工具 | Everything / Recoll（桌面） | ✅ | ✅ | 本机 | **手机端缺位** |
| **本软件** | 离线资料库 | ✅ **正文级 + 高亮** | ✅ **零权限零网络** | **本机私有沙箱** | 单机、无云同步（有意的） |

**能一句话说清的差异**：

> 能把正文级检索做到完全离线的，在手机端基本是空位；
> 能做到离线的，又大多不索引正文。

**答辩时可能被追问的点**（提前想好）：

| 追问 | 回答 |
|---|---|
| 系统备忘录不是能搜吗？ | 它主要搜标题与开头，长正文里的词搜不到。我们的示例资料 109 字都要切块建索引。 |
| 那用 Everything 之类的桌面工具？ | 桌面工具确实有，但手机上没有对等物，而且它们要文件系统全局权限，我们是零权限。 |
| 为什么不直接上云？ | 那是另一个产品。我们的约束是"数据不出设备"，上云就否掉了这个前提。 |

## 二、仓颉 P4：已有工作与空位（补"信号是几个"列）

18 条文献按**它解决哪个维度**分组。关键的第五列是我们要的空位。

| 组 | 代表工作 | 解决的问题 | 驱动信号 | **信号个数** |
|---|---|---|---|---|
| **工具维度** | TinyAgent [A1] | 工具检索降低 prompt 长度 | 相关度（检索） | **1** |
| | Tool Attention [A7] | 工具描述的注意力选择 | token 相关性 | **1** |
| | Tscg [A2] | 工具 schema 压缩 | 压缩率 | **1** |
| **消息维度** | LLMLingua 系列 [A16] | 提示压缩 | 压缩率 / 困惑度 | **1** |
| | Tscg [A2]（兼） | schema 压缩 | 压缩率 | **1** |
| **放置维度** | CAMPHOR [A3] | 端侧 SLM 规划 | 设备能力 | **1** |
| | CORE [A4] | 端云协作 | 隐私 / 预算 | **1–2** |
| | Hera [A6] | 设备–云协作 | 任务状态 + 自动子任务 | **1–2** |
| | Elastic On-Device [A5] | 模型装配与调度 | 资源 | **1** |
| | EcoAgent [A8] | 端侧放置 | 能耗 | **1** |
| | OpenPhone [A9] / PalmClaw [A10] | 端侧智能体框架 | 平台约束 | **1** |
| **成本/路由** | FrugalGPT [A11] | 成本–质量权衡 | 成本 | **1** |
| | RouteLLM [A12] | 请求路由 | 难度估计 | **1** |
| | Hybrid LLM [A13] | 混合推理 | 难度 | **1** |
| **协议** | MCP [A17] | 工具接入协议 | —（不是调度） | **0** |
| **本工作** | — | **三个维度统一调度** | **检索置信度 / 信息预算 / 网络状态** | **3** |

### 这张表要说明的一句话

> 已有工作几乎都是**一个维度、一个信号**。
> 把它们组合起来时，最常见的做法是压成一个"剩余预算"标量 —— 而这正是 P3 说的问题。
> **我们的空位是：三个维度各自用自己的信号，且这是必要的（不是可选的）。**

### 诚实标注

- 「信号个数」是**我按它解决的问题范围归的类**，原文未必这样表述
- Tscg 同时落在工具与消息两组（它压的是 schema，既省工具 token 也省消息 token）
- MCP 是协议不是调度方法，放在表里只为说明"工具接入"这一层已有标准，不重复造

## 三、答辩预判：这两张表最可能被问什么

| 可能的追问 | 建议回答 |
|---|---|
| 「信号个数」是你自己归的类吧？ | 是。依据是它解决的问题落在几个维度上。原文不会写"我用了 1 个信号"。 |
| 有没有真的用了两个信号的先前工作？ | CORE 与 Hera 可能是，但它们仍是**同一个决策**里混合，不是**分维度各自决策**。区别见 P5。 |
| 凭什么说三个信号不能合并？ | P8 的反面实验：压成单一信号后，成本降了但**在预算临界点出现失败**（0.45 档 0%）。 |
| 那你们的 0.45 档不也失败了吗？ | 是，而且原因尚未定位。但在基线上一档都降不下来成本——两者的失败方式不同。 |
