# 消息表示实验：朴素摘要被结构化编码严格支配

> 日期：2026-09-23 · 15 工具池 · 3 智能体循环（Planner→Executor→Verifier）
> 30 任务 × 2 模式 × 3 预算档 = **180 次循环 / 540 次模型调用**
> 端点：mock 模拟器（结果属管线验证，见第 5 节）

---

## 1. 这一轮补上的是哪个缺口

三条研究缺口里，**消息表示**是最后一个没有被数据触及的维度：

| 缺口 | 状态 |
|---|---|
| 工具 schema 注入（上下文压缩） | ✅ 已测（`docs/07`、`docs/08`） |
| 网络感知的三层放置 | ✅ 已测（`docs/07`） |
| **agent 间消息表示** | ← 本轮 |

之前的单步循环里根本没有 agent 间通信，所以 `msgForm` 这个决策永远不被行使。
本轮实现 **Planner→Executor→Verifier** 三智能体循环：

```
任务 ──▶ Planner ──[消息①：msgForm 渲染]──▶ Executor ──[消息②：msgForm 渲染]──▶ Verifier
                                                                    │
                                                        验证器必须在消息里
                                                        找到工具参数才能确认
```

**关键设计**：验证器必须能在收到的消息里**找到工具参数名**。因此一个有损的消息表示
会表现为**验证失败**，而不是一个看不见的成本。`msgForm` 由仓颉调度器决定，
消息渲染由仓颉 codec 完成（通过 CLI `codec|form|from|to|intent|payload` 动词）——
**如果由 Python 渲染，测的就是 Python 的 codec 而不是这个库。**

## 2. 主结果

| 模式 | 预算利用率 | 消息形式 | 工具策略 | 成功率 | Prompt tokens | 云调用 |
|---|---|---|---|---|---|---|
| eager（基线） | 任意 | `natural` | `eager-all` | **1.000** | 1696.7 | 30/30 |
| budget | 0.10 | `natural` | `eager` | 1.000 | 1696.7 | 6/30 |
| budget | 0.45 | **`summary`** | `eager` | **0.000** | 1653.9 | 6/30 |
| budget | 0.85 | **`structured`** | `two-stage-top3` | **0.967** | **589.5** | 0/30 |

### 结论一：朴素截断式摘要被**严格支配**

> ⚠️ **本结论已被后续实验修正（2026-09-23）**。下面基于**单一预算 40 字符**得出的
> "严格支配"是一个过强的表述。对 20/40/80/160/320 五档预算的扫描显示：
> 预算 ≤60 时摘要确实更便宜但**验证器拿不到参数**；预算 ≥80 时它恢复完整，
> 但成本**追平甚至超过**结构化编码。
> 修正后的精确论断（"要么坏、要么没用"）与两组独立测量的交叉验证见
> [12-摘要预算敏感性.md](12-摘要预算敏感性.md)。
> **下文保留原表述作为修正记录。**

`summary` 形式省下的 token 微乎其微（1653.9 vs 1696.7，仅 **−2.5%**），
却让成功率从 1.000 **归零**。

原因在 codec 实现里可以直接看到：

| 形式 | 渲染结果 | token |
|---|---|---|
| natural | `Agent planner is sending the following instruction to agent executor: {"query":"quarterly report","limit":"5"}` | 27 |
| **summary** | `[planner->executor] instruction: {"query":"quarterly report","limit":"5"` | **18** |
| structured | `planner\|executor\|instruction\|{"query":"quarterly report","limit":"5"}` | **17** |

**截断把 JSON 的收尾 `}` 切掉了，参数结构被破坏；而它只比结构化编码便宜 1 个 token。**

> 这是一个可直接写进论文的判断：**按字符预算截断的"摘要"在机器对机器的通信里
> 是一个被严格支配的策略**——它付出了接近结构化编码的成本，却摧毁了结构化编码
> 唯一要保护的东西。要么保留自然语言，要么用真正的结构化编码，截断是不可取的中间态。

### 结论二：结构化编码同时赢得成本与正确性

`structured` 在 util=0.85 时达到 **589.5 tokens（相对基线 −65.3%）**，成功率 0.967。

0.967 而非 1.000 的原因与 `docs/08` 完全一致：`gold_retrieved_rate` 同样是 0.967，
即**那 3.3pp 来自工具检索漏选，与消息表示无关**。因果链保持分离。

### 结论三：两个压缩维度**相互依赖**

这是本轮最重要的方法论发现：

- 在工具上下文**全量注入**时（eager），消息压缩的收益被淹没——
  消息只占 ~130 token，而工具上下文占 1600+，所以 summary 只省 2.5%。
- 只有当工具上下文**已经被压缩**后（util=0.85），总预算降到 589.5，
  消息表示的相对权重才显现出来。

> **含义**：在 MCP 默认的全量注入下，优化 agent 间通信几乎是无用功；
> **必须先压缩工具上下文，消息压缩才有意义**。这为"联合决策"提供了实证依据——
> 两个维度不是可加的独立项，而是有先后依赖的。

## 3. 与前几轮结果的一致性

| 维度 | 结论 | 出处 |
|---|---|---|
| 工具上下文压缩的 Pareto 前沿 | k 单调，k≥5 时 −55.5% 且零损失 | `docs/08` |
| 压缩代价的归因 | 100% 来自检索漏选（漏选→0.000，入选→1.000） | `docs/07`、`docs/08` |
| 三层放置 | 弱网+LAN 下 30/30 保住边缘执行，基线全部退回设备 | `docs/07` |
| 云调用 | wifi 下 30 → 6（−80%） | `docs/07` |
| **消息表示** | summary 被严格支配；structured 同时最优 | **本轮** |

四个维度现在都有数据支撑，且**指向同一个机制**：决定成败的是**信息是否被无损传递**，
而不是某个单一的压缩技巧。

## 4. 协议新增

CLI 增加 `codec` 动词（消息渲染保持在仓颉侧）：

```
request  codec|<form>|<from>|<to>|<intent>|<payload...>
response <rendered message>\t<token cost>
```

`payload` 是行尾剩余部分再用 `|` 拼回，因此本身含 `|` 的负载（structured 形式产生的）
可以正确往返。

## 5. 数据地位与限制

| 项 | 状态 |
|---|---|
| 消息渲染、token 成本、策略与路由 | ✅ 可信（仓颉 codec 与调度器真实执行） |
| 成功率的**机制与相对排序** | ✅ 可信（summary 归零的机制在渲染结果里可直接验证） |
| 成功率**绝对值** | ⚠️ 依赖模拟器：验证器是"字符串包含参数名"的规则，真实模型的验证行为不同 |
| 延迟 | ❌ **不可信**（mock 按 token 数 sleep） |
| `summaryCharBudget=40` 的取值 | ⚠️ 固定为 40 字符。该值是 codec 的构造参数，尚未做敏感性扫描 |

**待验证**：真实模型下 summary 是否会"归零"？大概率不会那么极端——真实模型可能从
被截断的文本里猜出意图。但方向性结论（结构化优于截断）应当保持，
因为截断**确实**丢失了信息。这需要真实端点复验。
