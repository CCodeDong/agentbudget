# 压缩代价实验：工具池规模是上下文压缩的调节变量

> 日期：2026-09-23
> 配置：30 任务 × 2 模式 × 3 网络档 × 3 预算档 = **540 次运行**（每轮）
> 三轮：5 工具池 → 15 工具池 → 15 工具池 + 检索归一化修复
> 端点：mock 模拟器（**结果仍属管线验证，非最终论文数字**，见第 6 节）

---

## 1. 这一轮要回答的问题

上一轮（5 工具池）的实验有个致命空白：**压缩是零代价的**——金标工具总能进 top-3，
所以"省 token"没有付出任何准确率代价。这使实验无法支撑论文的核心论点。

本轮把工具池扩到 **15 个**（加入 10 个真实可信的干扰工具：`sms.send`、`email.compose`、
`weather.query`、`alarm.create` 等），让 top-3 真正具有选择性，从而测出**压缩的代价**。

---

## 2. 主结果

### 2.1 三轮对比

| 轮次 | 压缩臂 Prompt tokens | 压缩臂成功率 | 基线 tokens | 基线成功率 |
|---|---|---|---|---|
| 5 工具池 | 398.3 | **1.000** | 584.4 | 1.000 |
| 15 工具池 | 510.9 | **0.900** | 1602.4 | 1.000 |
| 15 工具池 + 修复 | **526.2** | **0.967** | 1602.4 | 1.000 |

**核心发现（已修正，见下方警告）：上下文压缩的代价不是常数，而是随工具池规模出现的。**
5 个工具时压缩免费（−31.8% tokens，零损失）；15 个工具时出现 −3.3 个百分点的准确率代价，
换取 **−67.2%** 的 token 削减。

> ⚠️ **上述结论已被推翻（2026-09-24）。**
> 它比较的是**两套不同的检索实现**：第 26 行的 5 工具数据产生于检索归一化修复**之前**，
> 第 27/28 行产生于修复**之后**（本表下面的推进过程如实记录了这一点，
> 但结论那一行做了跨行比较）。
>
> 用**同一实现**重跑 5 工具池后：`398.3 tokens / 0.967`——与 15 工具池的代价**相同**
> （都是 30 个任务中损失 1 个）。
>
> **修正后的结论**：token 节省随池规模强烈增长（−31.8% → −67.2%），
> 而准确率代价不随池规模增长，且始终 100% 来自检索漏选（§3 的机制）。
>
> 发现方式：`tools/reproduce.py --check` 报告命令与数据不一致 → 重跑 → 逐行比对。
> 新数据：`experiments/results_pool5_fixed/`（旧数据 `results/` 保留为修前记录）。
> 论文对应修正：§6.1、摘要发现 1。

### 2.2 最终 Pareto 数据（15 工具池 + 修复）

| 模式 | 预算利用率 | 策略 | Prompt tokens | 成功率 | 云调用 |
|---|---|---|---|---|---|
| eager（基线） | 任意 | `eager-all` | 1602.4 | 1.000 | wifi 下 30/30 |
| budget | 0.25 | `eager`（余量充足，不压缩） | 1602.4 | 1.000 | 6/30 |
| budget | 0.55 | `two-stage-top3` | **526.2** | 0.967 | 6/30 |
| budget | 0.85 | `two-stage-top3` | **526.2** | 0.967 | 0/30 |

**Token 削减 −67.2%，准确率代价 −3.3pp，云调用削减 −80%。**

### 2.3 三层路由（弱网场景，与压缩无关的独立收益）

| 网络档 | eager 基线 | budget 调度器 |
|---|---|---|
| wifi + LAN | cloud ×30 | cloud 6 / edge 24 |
| 弱网 + LAN | **on-device ×30** | **edge ×30** |
| 弱网 + 无 LAN | on-device ×30 | on-device ×30 |

基线把"广域网不可用"等同于"无远程选项"，而局域网通常在广域网劣化时仍然存活。
调度器在弱网下保住了 30 次边缘执行，基线全部退回设备。

## 3. 因果链：损失**完全**来自检索，不是模型

对压缩臂按"金标是否入选 top-3"切分，两轮结果完全一致：

| | 修复前 | 修复后 |
|---|---|---|
| 金标**漏选** → 成功率 | **0.000** (n=18) | **0.000** (n=6) |
| 金标**入选** → 成功率 | **1.000** (n=162) | **1.000** (n=174) |

**没有一次失败发生在金标工具可用的情形下。** 也就是说：

> 压缩臂的准确率损失 **100% 由检索质量决定**，与模型能力、消息表示、路由都无关。

这是一个干净且可操作的结论：想让压缩更安全，应该改进**检索器**，而不是别的任何部分。

## 4. 发现并修复的检索缺陷

### 4.1 症状

修复前，恰好 3 个任务在全部 6 个压缩配置中恒定漏选：

| 任务 | 表述 | 实际选中 |
|---|---|---|
| `contact.lookup#2` | find the contact card for the person from the vendor | `weather.query\|web.search\|clipboard.read` |
| `contact.lookup#3` | search my contact list for the person from the vendor | `web.search\|weather.query\|clipboard.read` |
| `file.search#5` | find the file with the project proposal revision | `web.search\|weather.query\|clipboard.read` |

### 4.2 根因（实测确认，非推测）

选择器对**每一个词的出现次数**都累加分数，且**不过滤停用词、不去重**。

`"search my contact list for the person from the vendor"` 中 **"the" 出现两次**，
于是任何描述里含 "the" 的工具各得 **+6**：

| 工具 | 命中 | 得分 |
|---|---|---|
| `web.search` | "search" +3、"the"×2 +6 | **9** |
| `weather.query` | "the"×2 +6 | **6** |
| `clipboard.read` | "the"×2 +6 | **6** |
| **`contact.lookup`（正确）** | "contact" +3 | **3** ← 落选 |

**一个虚词的重复出现，压过了唯一的正确答案。** 这个假象解释了压缩臂的全部准确率损失。

### 4.3 修复

在选择器中加入**查询归一化**：小写化 → 停用词过滤 → **去重**。

```cangjie
func normalizeQueryWords(qLower: String): ArrayList<String> {
    let seen = HashSet<String>()
    let words = ArrayList<String>()
    for (w in qLower.split(" ")) {
        if (w.size >= 2 && !isStopword(w) && !seen.contains(w)) {
            seen.add(w)
            words.add(w)
        }
    }
    return words
}
```

### 4.4 修复效果

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 压缩臂成功率 | 0.900 | **0.967** | **+6.7pp** |
| 检索漏选 | 18 | **6** | −67% |
| 压缩臂 tokens | 510.9 | 526.2 | +3.0% |

**代价几乎为零（token +3%），恢复了三分之二的准确率损失。**

## 5. 残留损失：词法检索的语义盲区

修复后只剩 1 个任务恒定漏选：

```
web.search#3   "find online the release notes for the new version"
selected = calendar.create | contact.lookup | file.search
```

原因：归一化后查询词为 `{find, online, release, notes, new, version}`，
而**所有 15 个工具的名称与描述与这些词零重叠**，于是全部工具得分为 0，
选择退化为**工具池顺序**，取前三个。

> 这是词法检索的**根本局限**，不是缺陷：`online` 与 `web` 之间是语义而非字面关系。
> 模拟器之所以能选对，是因为它有显式同义词映射；仓颉选择器没有。

**这直接指明了下一步技术路线**：要么引入同义词/查询扩展，要么改用嵌入检索。
并且它给出了一个可量化的目标——当前 −3.3pp 的代价中，2/3 已由归一化消除，
剩余 1/3 需要语义能力才能消除。

## 6. 数据地位与限制（必须随结果一起引用）

| 项 | 状态 |
|---|---|
| prompt tokens、路由分布、云调用数、策略选择 | ✅ 可信（由真实 prompt 与仓颉引擎决定） |
| 成功率**的相对差异**与因果链 | ✅ 可信（诊断到"漏选即失败"的完全分离） |
| 成功率**绝对值** | ⚠️ 依赖模拟器的工具选择规则，真实模型下会不同 |
| 延迟 | ❌ **不可信**，由 mock 按 token 数 sleep 模拟 |
| 任务集代表性 | ⚠️ 自建 30 任务，审稿人会要求公开基准的可迁移子集 |

