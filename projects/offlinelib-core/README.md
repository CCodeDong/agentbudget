## 三、已实现的东西

### 3.1 切词（`src/tokenize.ts`）

**不依赖词典**——手机上没有中文分词词典，也不该为个人资料库塞一个几十 MB 的词表。

| 语言 | 做法 |
|---|---|
| 中文 | **单字 + 相邻二元组**（"离线资料库" → 离/线/资/料/库 + 离线/线资/资料/料库） |
| 英文/数字 | 按非字母数字切分，转小写 |

这是中文检索里的经典轻量做法：不用分词也能达到可用召回率，代价是索引约为字数的 2 倍词项。

**保留单字是一个刻意的取舍**：它让"单字查询"也能工作，但也意味着
**几乎任何中文查询都会命中某个常用字**（如"的"）。BM25 的高 DF 会压低这类词的 IDF，
所以排序不受影响，但**"完全无结果"在中文场景下很罕见**——测试里用纯 ASCII 串来构造这个用例。

### 3.2 倒排索引 + BM25（`src/index.ts`）

- 标准 BM25：`k1 = 1.5`，`b = 0.75`
- 倒排表存**词频 + 位置**，位置用于高亮
- 重复加入同一块是幂等的（便于增量建库）
- **打分不截断**——返回全部候选，因为自适应 top-k 需要看完整分布才能找断层

### 3.3 分块（`src/index.ts`）

- 默认每块 240 字符、相邻块重叠 40 字符
- 重叠是必需的：中文关键词被切在块边界上会导致漏检

### 3.4 自适应 top-k（`src/search.ts`）⭐

**这是把研究结论产品化的部分。**

```
固定 k      → kSource: 'fixed'      （对照组）
得分分布驱动 → kSource: 'score-gap'  （我们的方法）
```

规则：

1. 找相邻得分的**最大相对落差**位置 `g`
2. 若落差 ≥ 5%，取 `k = g + 1`（断层之前的全部保留）
3. 若分布平坦（无可信断层）→ 取上界 `maxK`
4. 最后夹到 `[minK, maxK]` 与候选总数内

> 为什么用**相对落差**而不是绝对差：不同查询的得分量级不同，只有相对值可比。

### 3.5 预算决策（`src/search.ts`）

`decideBudget()` 回答的是**另一个问题**：

| 函数 | 回答的问题 | 看的信号 |
|---|---|---|
| `decideKByScoreGap` | **该取几条**（信息层面） | 得分分布 |
| `decideBudget` | **还取得起吗**（资源层面） | 延迟 / 内存 / 电量 |

**这正是我们研究主张的另一半：两个问题需要两个不同的信号。**
把它们混成一个"剩余预算"信号，就会得到实验里那个被严格支配的结果。

## 四、测试（34 个）

覆盖：切词、分块、索引、BM25、高亮、自适应 k、预算决策、边界条件。

**过程中发现自己写错的 4 个测试**（不是代码错，是测试错）：

| 错的测试 | 错在哪 |
|---|---|
| BM25 命中块排序 | 加入的资料**不含查询词** |
| 自适应 k 三重夹紧 | 断言"上界大时 k 会变大"——**夹紧只会压低，不会抬高** |
| 固定 k 模式 | 只有 1 个块命中，k 被正确夹到 1，而测试期望 2 |
| 无结果 | 中文单字索引让"无关查询"仍能命中常用字 |

> **保留这段记录是刻意的**：它说明测试是真的在跑，而不是摆设。

## 五、与 ArkTS 的兼容性

本模块**刻意只使用 ArkTS 支持的子集**：

| 约束 | 原因 |
|---|---|
| 不用 `any` | ArkTS 禁止 |
| **不导入任何 HarmonyOS Kit** | HMS Kit 在缺少 HSP 的设备上会让**整个应用在加载期崩溃**（我们实测过，崩溃日志在案） |
| 用 `Map` 而非 `Record<string, X>` | ArkTS 拒绝给索引签名类型赋对象字面量（`arkts-no-untyped-obj-literals`） |
| 无动态导入、无 `eval` | ArkTS 禁止 |

因此这些 `.ts` 文件**可以原样放进 ArkTS 工程的 `ets/` 目录**（需验证，见下）。

## 七、和软著的关系

老师指出的最大短板是"软著计划缺失"。而**软著登记需要"体现软件功能逻辑的源代码"**。

这个模块现在是 **634 行源码 + 330 行测试**、34 个测试、覆盖 4 个核心功能——
**它本身就是一个可以拿去登记的真实软件，而不是空壳。**

若走"先搭骨架再登记"的路线，还需要补：

| 缺什么 | 大概行数 |
|---|---|
| 最小 UI（导入 → 建索引 → 搜索 → 显示结果） | ~500 |
| OCR 接口层（可先用假数据） | ~100 |
| 索引持久化 | ~200 |
| **合计** | **~800** |

补齐后约 **1,400 行源码**。

> **关于行数要求**：软著登记要求提交**前 30 页 + 后 30 页源代码（每页 50 行）**，
> 不足 60 页则提交全部。所以 1,400 行会走"提交全部"的路径——**这是允许的**，
> 但审查会看"是否体现软件功能逻辑"，因此**宁可多写有意义的代码，不要凑行数**。
